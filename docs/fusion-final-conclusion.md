# 进程融合流水线最终结论

经过多轮实际测试和验证，现在给出最终评估。

## 测试结果总结

### 测试 1: Shell 脚本分批流水线
**结果：** 失败
**原因：** 容器生命周期问题，后台进程被杀

### 测试 2: 监控文件系统提前启动
**结果：** 失败  
**原因：** InterfaceCOLMAP 需要完整的图像集

### 测试 3: 部分图像测试
**结果：** InterfaceCOLMAP 报错，无法处理缺失文件
**原因：** 它会尝试读取 sparse model 中列出的所有 41 张图像

## 核心障碍

1. **InterfaceCOLMAP 是瓶颈**
   - 它从 `sparse/images.bin` 读取完整的 41 张图像列表
   - 然后在 `dense/images/` 中查找这些文件
   - 缺失任何一张都会失败或跳过

2. **COLMAP undistorter 不可分割**
   - 没有 `--image-range` 参数
   - 必须处理完整的 sparse model

3. **OpenMVS DensifyPointCloud 需要邻居视图**
   - 图像 i 需要访问图像 i±2 左右的邻居
   - 如果邻居缺失，深度图质量下降或失败

## 唯一可行的方案

**完整的进程融合（库级集成）**

```
不经过磁盘文件：
  COLMAP undistort (内存) → 内存队列 → OpenMVS densify (内存)
  
绕过 InterfaceCOLMAP：
  手动构建 OpenMVS Scene 对象，不从 scene.mvs 加载
```

### 实现复杂度

1. **链接两个库** (1-2天)
   - 处理 Eigen、OpenCV、CUDA 版本冲突
   - 配置 CMake
   
2. **数据结构转换** (1天)
   - COLMAP `Reconstruction` → OpenMVS `Scene`
   - COLMAP `Camera` → OpenMVS `Platform`
   - 位姿转换（world-to-camera vs camera-to-world）

3. **内存队列和线程同步** (1天)
   - 生产者-消费者模式
   - 背压控制
   - 错误传播

4. **调用 OpenMVS 内部 API** (1-2天)
   - `EstimateDepthMap()` 是私有方法
   - 需要 hack 或重构代码
   - 处理邻居视图缓存

5. **测试和调优** (1天)
   - 验证正确性
   - 性能调优
   - 边界情况

**总计：5-7 天全职开发**

## 我的最终建议

**不实施进程融合，理由：**

1. **边际收益递减严重**
   - 已经获得 -23%，再投入 1周只能多省 11%
   - 累计 -34% vs 投入 5分钟+1周

2. **维护成本高**
   - 两个大型库的紧密耦合
   - 上游更新时需要同步修改
   - 调试困难（融合后的 bug 难定位）

3. **有更好的替代方案**
   - **更激进参数**：5分钟，再省 5-8%
   - **算法升级**：长期投资，潜力更大（2-5x）
